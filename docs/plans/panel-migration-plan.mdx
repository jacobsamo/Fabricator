This is the migration plan for introducing `apps/panel` as Fabricator's new installed dashboard while keeping the current Vue dashboard in `apps/frontend` during the transition.

The goal is to ship a faster, more maintainable control panel without changing the backend API contract or making release installs more complex.

## Direction

Create a new app at `apps/panel`.

Keep `apps/frontend` in place until the panel reaches feature parity. The Vue app remains useful as the reference implementation while each screen is ported.

When the panel is ready, change production serving and release packaging from `apps/frontend/dist` to `apps/panel/dist`. Until then, the backend should continue serving the current frontend.

Use this stack for `apps/panel`:

The website already uses the visual direction we want: Base UI, shadcn, Tailwind v4, lucide icons, Geist, and the orange/neutral Fabricator theme. The panel should reuse that theme vocabulary, then tune it for a dense application UI instead of a marketing page.

## shadcn Strategy

Install shadcn in `apps/panel` and add the full component set early.

The important point is that shadcn components become local source code. We should use that as the starting system, then adjust the local components to match Fabricator's product feel.

Use shadcn for:

- buttons
- inputs

- sidebar
- tables

After install, tune the local shadcn files rather than wrapping everything in another design system. For example:

- `button.tsx` can carry Fabricator-specific size, radius, loading, and icon defaults.
- `accordion.tsx` can differ from the marketing site if the panel needs denser disclosure rows.
- `select.tsx` and `dropdown-menu.tsx` should be tuned for keyboard-heavy operations.
- `sidebar.tsx` should become the foundation for Fabricator's app chrome.
- `breadcrumb.tsx` should use TanStack route matches and server names.

Keep changes token-driven. Prefer semantic classes such as `bg-background`, `text-muted-foreground`, `border-border`, and `text-primary` over raw color utilities.

## App Boundary

`apps/panel` is the product dashboard. `apps/website` remains the public marketing and docs site.

Do not fold the installed panel into the website app. The panel should stay a standalone Vite SPA served by Flask, because that keeps native installs, Docker images, Windows builds, and self-update simple.

The production contract should eventually be:

```text
apps/panel/dist -> bundled as frontend/dist or served directly as panel/dist
Flask fallback route -> index.html
/api/* -> JSON API only
```

During migration, keep the current contract:

```text
apps/frontend/dist -> served by Flask
apps/panel -> development app only
```

## Static Route Splitting

The panel should code split by route while remaining a plain static SPA.

Use TanStack Router route components with `lazyRouteComponent` for page-level modules. Vite turns these dynamic imports into hashed files under `dist/assets`, so self-hosted installs and Docker containers only need to serve the static build directory. No SSR, CDN, or runtime bundler is required.

The current route chunk policy is:

- keep root providers, auth guards, query client, app shell, and route declarations in the entry graph
- lazy-load `/`, `/login`, `/setup`, and each `/server/$serverId/*` page module
- group shared libraries with Vite `build.rolldownOptions.output.manualChunks`
- keep React, TanStack, UI helpers, and generic vendor modules in cacheable vendor chunks
- rely on TanStack Router `defaultPreload: "intent"` so likely route chunks are prefetched on user intent without loading the whole app upfront

Static serving requirements:

- `dist/index.html` must reference only local `dist/assets/*` files.
- Flask must serve unknown non-API app routes to `index.html`.
- Flask/Docker/PyInstaller must serve `dist/assets/*` with long-lived cache headers where practical.
- A deploy/update may replace old hashed chunks; TanStack's lazy component wrapper handles stale chunk URLs by attempting one page reload on module-not-found.
- Packaged smoke tests must refresh deep links such as `/server/<id>/files` and prove lazy chunks load from the packaged static server, not only from Vite dev.

## Update Safety Contract

The in-app update path must keep working exactly as it does today. A user should be able to click update, let `tools/update.sh` run the release installer, and come back to the same backend, data, settings, auth mode, server records, playit state, Java installs, backups, and update service behavior. The only intended difference at panel cutover is the improved UI served from the same backend.

For the first panel release, keep the installed runtime layout compatible:

```text
release CI builds apps/panel/dist
release artifact is still named frontend-dist
Linux tarball still contains frontend/dist
Docker runtime still copies the UI to ./frontend/dist
PyInstaller still bundles frontend/dist
Flask still serves frontend/dist
```

This avoids changing both the UI implementation and the runtime static path in one release. A later cleanup release can rename the runtime bundle from `frontend/dist` to `panel/dist` if it is still worth the churn.

Before changing release packaging, test these update cases:

- Existing native install updates from a Vue-dashboard release to a panel-dashboard release.
- Existing Docker install pulls the new image and keeps the `/data` volume intact.
- Existing Windows build bundles the panel as `frontend/dist` and still serves deep links.
- Auth-enabled install remains logged-in/session-compatible where expected; logged-out users land on `/login`.
- First-boot install with no password still lands on `/setup`.
- Auth-disabled install still bypasses the guard.
- Existing deep links such as `/server/<id>/overview` still work after update and browser refresh.
- Unknown `/api/*` paths still return JSON 404 instead of the SPA HTML.
- Unknown non-API app routes still fall back to `index.html`.
- Failed update attempt leaves the previous installed app intact, or at minimum keeps `fabricator.service` restartable with clear update logs.

Release cutover should be blocked unless the new panel passes the same smoke flows against a packaged artifact, not only against the Vite dev server.

## Testing Without Local Minecraft Servers

Do not require contributors or release verification to create real Minecraft servers on their host machine. Most panel work can and should be tested with deterministic fixtures.

Use four layers:

1. UI fixture mode in `apps/panel`.
   Mock `/api/*` responses with a browser-level mock layer such as MSW, backed by checked-in auth, setup, server, player, mod, file, backup, playit, and update fixtures. This is the fastest loop for styling, navigation, forms, empty states, loading states, and error states.

2. Backend fixture mode.
   Run the Flask backend against a temporary data directory and fake server records, with background schedulers and real process starts disabled. This verifies API shape, auth cookies, SPA fallback, and route guards without creating or launching Minecraft.

3. Packaged Docker smoke tests.
   Build the same artifact shape users receive, copy `apps/panel/dist` into runtime `frontend/dist`, mount a disposable `/data` volume, seed fixture data, and run Playwright against the Flask-served panel. This verifies update safety, refresh/deep-link behavior, static serving, and auth/session behavior in an install-like environment.

4. Narrow real-server tests.
   Keep true Minecraft create/start/stop tests as opt-in release or nightly checks in an isolated container or VM. They should not be part of the normal panel UI development loop.

Required panel smoke coverage:

- `/` decides once between app, setup, and login from `/api/auth/status`.
- Unauthenticated app routes redirect straight to `/login?redirect=...`.
- First-boot installs redirect straight to `/setup`, not login then setup.
- Auth-disabled installs enter the app without login.
- Login and setup mutate auth state locally and navigate client-side without a full page reload.
- Server deep links refresh correctly from the packaged Flask server.
- Empty server list, populated server list, stopped server, running server, installing server, and API error states all render from fixtures.
- Update status and update-trigger UI render from fixtures without modifying the host machine.

## Query Cache and Auth Boundaries

Use predictable query-key roots so auth, logout, and future team auth stay easy to reason about:

```text
["auth", "status"]       install/auth status used by route guards
["session", ...]         protected data for the active authenticated context
```

Rules:

- Login and setup set `["auth", "status"]` to authenticated immediately after a successful mutation.
- Logout clears all `["session", ...]` queries, clears mutation state, writes unauthenticated auth status, then navigates to `/login`.
- Global `401` handling uses the same session-clearing path as logout before redirecting.
- Route data must use the `queryKeys` helpers, not ad hoc string arrays.
- Future team/org auth should extend the session root instead of changing the logout mechanism, for example `["session", teamId, "servers"]` or `["session", orgId, "servers"]`.
- Switching team/org/account should clear the previous scoped `["session", ...]` data before loading the next scope, while keeping `["auth", "status"]` intact.
- Do not store protected server data under `["auth", ...]`; auth keys are only for authentication/install status.

## TanStack Primitive Decisions

Use TanStack primitives deliberately. The goal is a small set of deep modules with clear interfaces, not a new global store wrapped around every feature.

| Primitive | Use in Fabricator panel | Why |
| --- | --- | --- |
| TanStack Router | Required | Own URL shape, route guards, params, search params, route-level loading, route context, and route code splitting. |
| TanStack Query | Required | Own server state: backend reads, mutations, cache invalidation, polling, retries, and background refresh. |
| TanStack Store | Required for client/UI state | Replace Pinia-style UI state where state is not server-owned: command palette, modal host, selected mods, file editor dirty state, route-local wizard state, hotkey scopes, sidebar UI state. |
| TanStack Form | Required for forms | Every form should have typed validation and submission state with Zod schemas. |
| Zod | Required | Parse risky backend responses and validate every form. |
| TanStack Hotkeys | Required but scoped | Command palette, route navigation, refresh/search shortcuts, safe submit shortcuts. No destructive single-key actions. |
| TanStack DB | Deferred, adapter candidate | Consider after Query ports if normalized live collections would simplify servers/mods/players/backups. It should not block parity because the backend is REST and current screens can be cleanly represented by Query plus Store. |
| TanStack Table | Use when table behavior gets real | Backups snapshots, players, mods, and files can use it when sorting/filtering/selection complexity justifies it. |
| TanStack Virtual | Optional | Use only if large files/mods/players/snapshot lists make rendering expensive. |
| TanStack Pacer | Optional | Use for debounced Modrinth search, file search, and throttled high-frequency UI actions if local helpers become messy. |

State ownership rules:

- Server-owned data belongs in TanStack Query.
- Client-only UI state belongs in TanStack Store.
- Form draft/validation state belongs in TanStack Form.
- URL-visible state belongs in TanStack Router search params.
- Normalized collection state may belong in TanStack DB only after a feature proves it needs local relational queries/live collection updates.

Initial Store modules:

```text
src/stores/app-store.ts          command palette, global modal host, sidebar state
src/stores/server-ui-store.ts    selected server UI state, active modal ids, transient action state
src/stores/file-editor-store.ts  open file, content, original content, dirty/discard state
src/stores/mods-ui-store.ts      selected mod paths, search text, pending mod/modpack dialogs
src/stores/backups-ui-store.ts   selected snapshot/config, upload progress, restore modal state
src/stores/hotkeys-store.ts      active scopes and command palette registration metadata
```

Keep Stores narrow. If a Store starts mirroring backend data, move that data back into Query or a DB collection.

TanStack DB evaluation gate:

- Do not introduce DB in the first parity port.
- Re-evaluate DB when at least two pages need the same normalized data with different live projections, such as server summaries plus current server detail plus sidebar status, or player state plus online player updates plus per-row mutations.
- If adopted, wrap DB collections behind `src/data/collections/*` so route code does not know whether data came from Query-only or Query-backed collections.

## Vue Compliance Gate

A React route or component is only Vue-compliant when all of these are true:

- The Vue source file has been read and mapped to the React implementation.
- The React UI renders the same core data, empty states, loading states, disabled states, and backend-error states.
- Every Vue mutation has an equivalent React mutation with matching success feedback, error feedback, query invalidation, and rollback behavior where Vue used optimistic state.
- A simulated `401` from that feature clears protected `["session", ...]` data and routes through the same auth boundary as logout.
- Polling starts, stops, and changes cadence for the same reasons as Vue.
- Dialogs, confirmations, destructive actions, and dirty-state guards cannot lose user work silently.
- At least one fixture or route test covers the happy path, failure path, and auth-expiry path for the feature.
- The panel still passes `bun run types:check`, `bun run test`, `bun run lint`, and `bun run build`.

Current compliance blockers:

- Vue parity capture tests/screenshots do not yet exist for the highest-risk current flows.
- Create-server/install progress is closer to Vue parity, but optional modpack setup during create and broader Java/install failure continuation tests remain open.
- Advanced Modrinth/modpack flows still need dependency, compatibility, missing-file, and uncertain-side continuation coverage.
- Backup job polling has route coverage for quick backup and terminal-state display, but retained/deleted/purged file result coverage remains open.
- Java install progress and managed-Java removal have first route tests; Java terminal success toast polish and full state-machine coverage remain open.
- Backend static fallback tests exist, but packaged Flask/Docker smoke tests still need to prove the split panel loads from `frontend/dist` after refresh/deep-link navigation.

Fixture and parity coverage:

- Expand MSW fixtures for running, stopped, pending, installing, failed, auth-expired, API-error, empty-list, and large-list states.
- Add React route tests for every server page: overview, console, files, players, mods, backups, playit, properties, and settings.
- Add Vue parity capture tests or screenshots for the highest-risk flows before replacing the shipped frontend.
- Add packaged Flask/Docker smoke tests that serve the built `apps/panel/dist` as `frontend/dist` and refresh deep links for every route.

Mutation rollback and session expiry:

- Players: whitelist/op/ban/kick/IP-ban success, backend failure rollback, and 401 session expiry.
- Mods: single delete, bulk delete, Modrinth install, failed install, and 401 session expiry.
- Files: save success, save failure, dirty discard, route-change protection, and 401 session expiry.
- Backups: config save/delete, quick backup, restore, import-world upload failure, job failure, and 401 session expiry.
- Settings/properties/password: dirty state, validation errors, backend errors, running-server edit guard, and 401 session expiry.

Polling and backend state machines:

- Server shell polling must preserve Vue's effective-status precedence when an action is in flight.
- Console/log polling must pause or reduce cadence when the route is not active.
- Players online polling must only run while the server is running.
- Backup job polling must stop on terminal states and surface retained/deleted/purged file results.
- playit polling must match the daemon lifecycle: unsupported, stopped, starting, running, claim-required, error.
- Java install polling must cover checking, needs-Java, downloading, installing, done, error, and managed-Java removal.
- Update polling must cover idle, update-available, in-progress, success, failure, and self-update-disabled states.

Modpack and Modrinth parity:

- Dependency dialog: install dependencies, install main only, cancel.
- Compatibility dialog: no exact version, compatible version selected, no compatible version.
- Mod side decisions: all-server, all-client, per-file choices, unresolved choices blocked.
- Missing-file continuation: accepted skipped files, cancelled install, backend failure.
- Replace install: backup option on/off, Java warning, install-progress polling, failed install recovery.

- login, logout, setup, change password
- create server, delete server
- install server
- start, stop, restart
- update server settings
- set autostart
- send console command
- install/remove mods
- install modpacks
- browse/save files
- create/update/delete backup configs
- quick backup
- restore snapshot
- import world
- player whitelist/op/ban/kick actions
- playit start/stop/reset
- trigger Fabricator update

Mutations should invalidate the smallest useful query set. For example, starting a server invalidates `['server', serverId]` and may leave mods/backups untouched.

Highest-priority Zod schemas:

- server list and server detail
- server install progress
- Java status and Java install progress
- Modrinth search/detail/install errors
- backup config, snapshot, summary, and job progress
- player state
- playit status
- update status

## Polling

Use TanStack Query polling instead of hand-managed intervals.

Suggested intervals:

| Data | Interval |
| --- | --- |
| Current server status | 2500 ms while viewing a server |
| Logs | 4000 ms on overview and console |
| Modpack install progress | 1500 ms while active |
| Java install progress | 1500 ms while active |
| Backup/import job progress | 1500 ms while active |
| Update status | 15 minutes when idle |
| Update status during active update | 4000 ms |

Avoid global polling for pages that are not visible. Route-level code splitting and query enablement should keep the app light.

## Performance Rules

The panel should stay fast by default:

- SPA build with Vite.
- Route-level code splitting.
- Lazy-load heavy feature pages and modals.
- Keep Modrinth browser and modpack browser out of the initial route bundle.
- Keep file editor logic out of routes that do not need it.
- Import lucide icons directly.
- Avoid large chart/editor libraries unless the feature needs them.
- Use TanStack Query cache instead of duplicated global stores.
- Use query `enabled` flags so hidden routes do not fetch.
- Use `staleTime` for data that does not need live polling.
- Keep table virtualization as an option for large mods/files/player lists.
- Track bundle size with Vite output and add bundle analysis before cutover.

Initial performance targets:

- initial dashboard JavaScript under 250 KB gzip where practical
- server route shell interactive quickly on local hardware
- heavy panels split into separate chunks
- no polling from hidden routes
- no marketing-site code in the installed panel
